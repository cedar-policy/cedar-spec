# A Rust model of Cedar, verified against production and the Lean spec

This directory holds a simplified, executable Rust model of Cedar and the
proofs that connect it to the production Rust implementation (`cedar/`) and
to the Lean specification (`../cedar-lean`). The model and the proofs cover
`cedar-policy-core`'s `Evaluator` and `Authorizer`, with the extension
functions, and the public `cedar_policy::Authorizer::is_authorized`.

The chain has four links:

```
production Rust  ==(Verus)==  Rust model  ==(Aeneas)==>  Lean model  ==(Lean)==  Cedar.Spec
     (cedar/)                 (src/*.rs)                 (lean/)                (cedar-lean/)
```

1. **Production ≡ model** (Verus). `cedar/cedar-policy-core/src/verification/mod.rs`
   includes `src/lib.rs`, and with it every module of the model, as the
   module `verification::model` (with `#[path]`). The model's functions are
   also spec functions (`dual_spec`), and the production functions carry
   `verus_spec` contracts stated with them.
2. **The model in Lean** (Aeneas). `scripts/extract.sh` translates
   `src/*.rs` into `lean/CedarRustModel/{Types,Extracted}.lean`.
3. **Model ≡ spec** (Lean). This is proved in `lean/CedarRustModel`.
4. **The theorems.** The authorization theorems of `Cedar/Thm` are
   - restated about the model in Lean;
   - transcribed as Verus axioms (`verification/authorizer_lean_theorems.rs`);
   - proved about the production functions in Verus
     (`verification/authorizer_theorems.rs` in `cedar-policy-core`, and in
     `cedar-policy` for the public API).

What is assumed is listed in [TRUSTED.md](TRUSTED.md).

## Layout

The model has one module per file of `cedar-lean/Cedar/Spec`, and each
component of the proofs has its own files, named after the component.

- `src/`: the model.
  - `value.rs`: values and errors, with copying, equality, the Lean
    ordering, canonical forms (sets and records are lists in canonical form,
    as in Lean) and lookups;
  - `expr.rs`, `request.rs`, `entities.rs`: expressions, requests and entity
    stores;
  - `evaluator.rs`: `evaluate`;
  - `authorizer.rs`: `satisfied`, `is_authorized`;
  - `policy.rs`: static and template-linked policies (Lean's
    `Cedar.Spec.Policy`), `Policy.toExpr` (`policy_to_expr`, with the
    folding `Expr.mkAnd`) and `to_policy`;
  - `ext.rs`: the extension types and functions (`decimal`, `ipaddr`,
    `datetime`, `duration`), parsers included.
- `lean/CedarRustModel/`: the Lean proofs.
  - `Types.lean`, `Extracted.lean`: generated by `scripts/extract.sh`;
  - `FunsExternal.lean`: two hand-written primitives;
  - `Convert.lean`: the translation of model values to `Cedar.Spec`;
  - `Lemmas/`: lemmas about the model;
  - `Evaluator.lean`, `Authorizer.lean`, `Policy.lean`, `Ext/`: the
    correctness theorems of each component;
  - `Theorems/`: the `Cedar/Thm` theorems about the model
    (`Authorization.lean`).
  - `../CheckAxioms.lean` lists the exported theorems.
- `../cedar/cedar-policy-core/src/verification/`: the Verus proofs.
  - `abs.rs`, `value_abs.rs`, `expr_abs.rs`, `policy_abs.rs`, `ext_abs.rs`:
    abstractions from production to the model;
  - `map_entries.rs`: sorted map entries;
  - `*_lemmas.rs`: lemmas;
  - `trusted.rs`, `ext_trusted.rs`, `authorizer_lean_theorems.rs`: the
    assumptions;
  - `authorizer_theorems.rs`: the theorems.
- `../cedar/cedar-policy/src/verification/`: the public API's contract and
  theorems.
- `scripts/`: `extract.sh`, `check_axioms.sh`, `verus_core.sh`,
  `verus_api.sh`, `check_all.sh`.

## The theorem chain

### 1. Model ≡ Lean spec (Lean, `lean/CedarRustModel`)

Exact, on all inputs, with extension values and calls (no well-formedness
hypotheses):

```lean
theorem evaluate_correct (x : expr.Expr) (req : request.Request)
    (es : value.List (value.EntityUID × entities.EntityData)) :
    ∃ r, evaluator.evaluate x req es = .ok r ∧
      Result.toSpec Value.toSpec r =
        Cedar.Spec.evaluate (Expr.toSpec x) (Request.toSpec req) (Entities.toSpec es)

theorem is_authorized_correct (req : request.Request)
    (es : value.List (value.EntityUID × entities.EntityData))
    (ps : value.List authorizer.Policy) (lps : List Cedar.Spec.Policy)
    (hps : List.Forall₂ Policy.Corresponds (List.toList ps) lps) :
    ∃ r, authorizer.is_authorized req es ps = .ok r ∧
      Response.toSpec r = Cedar.Spec.isAuthorized (Request.toSpec req) (Entities.toSpec es) lps

theorem to_policy_correct (p : policy.LinkedPolicy) :
    ∃ q, policy.to_policy p = ok q ∧ Policy.Corresponds q (LinkedPolicy.toSpec p)
```

`Policy.Corresponds q lp` says that `lp` has the ID and effect of `q`, and
that `lp.toExpr = Expr.toSpec q.condition`. The extensions are covered by
- `call_correct` (`ext.call f args` is `Cedar.Spec.call`);
- `ext_eq_correct` and `ext_lt_correct`;
- the parser theorems (`parse_decimal_correct`, `parse_ip_correct`,
  `parse_datetime_correct`, `parse_duration_correct`).

### 2. Authorization theorems about the model (Lean, `Theorems/Authorization.lean`)

The theorems of `Cedar/Thm/Authorization.lean` and `PolicySlice.lean`, stated
about `authorizer.is_authorized` for policy lists `ps` with `Linked ps` (every
policy is `policy.to_policy` of a linked policy):
`forbid_trumps_permit`, `allowed_only_if_explicitly_permitted`,
`default_deny`, `allowed_iff_explicitly_permitted_and_not_denied`,
`denied_iff_explicitly_denied_or_not_permitted`, `order_and_dup_independent`,
`unchanged_allow_when_add_permit`, `unchanged_deny_when_add_forbid`,
`is_authorized_eq_for_sound_policy_slice`, `determining_policies_of`,
`erroring_policies_of`, `determining_erroring_disjoint_when_unique_ids`.
For example:

```lean
theorem forbid_trumps_permit (req) (es) (ps : value.List authorizer.Policy) (hl : Linked ps) :
    IsExplicitlyForbidden req es ps →
    ∃ r, authorizer.is_authorized req es ps = ok r ∧ r.decision = .Deny
```

All 25 exported Lean theorems use only `propext`, `Classical.choice` and
`Quot.sound` (`scripts/check_axioms.sh`).

### 3. Production ≡ model (Verus)

The contracts, with `m` the model:

- `Evaluator::partial_interpret(expr, slots)`, and likewise `interpret` with
  `result_rel`:
  ```
  requires self.spec_wf(), !stack_exhausted(), expr_modeled(*expr, *slots, self.spec_ext_ok())
  ensures  pv_result_rel(r, m::evaluator::evaluate(&abs_expr(*expr, *slots), &self.spec_request(), &self.spec_entities()))
  ```
  Both succeed with the same value, or both fail. The requirements are:
  - `spec_wf`: a concrete request and entity store;
  - `expr_modeled`: no unknowns, slots bound, and extension calls only with
    all the extensions.

  The same holds for `unary_app`, `binary_relation`, `binary_arith`, every
  `eval_*` arm, and every extension function against `ext::call`.
- `Evaluator::evaluate(p)`: `Ok(b)` iff the model evaluates the policy's
  condition to `b`, and `Err` iff the model's evaluation is not a boolean.
  - It requires `policy_modeled(*p, self.spec_ext_ok())`.
  - The model policy is `abs_policy(p) = policy::to_policy(&abs_linked_policy(p))`.
- `TemplateBody::condition` / `Template::condition` / `Policy::condition`:
  `body_cond_rel(r, body)`. In every slot environment in which the policy
  is modeled, the condition is modeled, and its model is
  `policy::policy_to_expr` of the linked policy.
- `Authorizer::is_authorized(q, pset, entities)`:
  ```
  requires request_wf(q), entities_wf(*entities), policy_set_modeled(*pset, self.spec_ext_ok()), !stack_exhausted()
  ensures  response_rel(r, m::authorizer::is_authorized(&abs_request(q), &abs_entities(*entities), &abs_policy_set(*pset)))
  ```
  This means the same decision, the same determining policies, and the same
  erroring policies. `Authorizer::new()` ensures `spec_ext_ok()`.
- The public `cedar_policy::Authorizer::is_authorized(r, p, e)`: under the
  same hypotheses on the core values, its response is the lift
  (`response_lift`) of a response of the core `Authorizer::is_authorized`
  on the same arguments (`is_authorized_lift`).

### 4. The theorems about production (Verus)

`verification/authorizer_theorems.rs` proves the same twelve theorems
(`thm_*`) about the result `r` of `Authorizer::is_authorized` (`authorized(a,
q, ps, es, r)`: `call_ensures` under its preconditions). A policy is
*satisfied* when the production evaluator returns `Ok(true)` on it, and
*errors* when it returns `Err`. For example:

```
thm_forbid_trumps_permit: is_explicitly_forbidden(q, es, ps) ==> r.decision is Deny
```

`cedar-policy/src/verification/authorizer_theorems.rs` states them about the
public `Authorizer::is_authorized`, on the core values of its arguments.

## Building and checking

Requirements: Verus 0.2026.10.18 (`VERUS_DIR`, default
`~/tools/verus-dl/verus-x86-linux`) with Rust 1.99.1; Charon/Aeneas at the
commit in `lean/lakefile.lean` (`AENEAS_DIR`, default `~/tools/aeneas-dl`);
Lean 4.35.0 through `elan`.

`scripts/check_all.sh` runs everything: extraction (and a check that the
committed Lean files are up to date), the `cedar-lean` build and unit tests,
`lake build CedarRustModel` (failing on `sorry`), the axiom check, Verus on
`cedar-policy-core` and on `cedar-policy`, `cargo test` of both crates, and
clippy (set `CLIPPY_BASELINE` to an upstream checkout to compare warnings).
Build products and logs go to `../.build` (`BUILD_DIR`).

Each step can also be run alone. `scripts/verus_core.sh` passes its arguments
to Verus, e.g. `--verify-only-module evaluator --verify-function
binary_relation`. Verus takes about 30 seconds on `cedar-policy-core` and 10
on `cedar-policy`; `check_all.sh` takes under 2 minutes with warm caches, and
about 10 more from scratch for the Lean builds.

## The Lean spec (`cedar-lean`)

The Lean spec agrees with production in two places where the proofs need it:

- `Policy.toExpr` and `Conditions.toExpr` fold a conjunction of two boolean
  literals (`Expr.mkAnd`), as production's `Policy::condition`
  (`ExprBuilder::and`) does, so the spec's policy expression is production's.
  `evaluate_mkAnd` and `evaluate_policy_toExpr` show that it evaluates like
  the unfolded conjunction.
- `Ext.lt` orders extension values of different types by type name
  (`datetime < decimal < duration < ipaddr`), as production's evaluator does.
  SymCC uses `Ext.symccLt` (`decimal < ipaddr < datetime < duration`), the
  order of production SymCC; `Thm/SymCC/Data/LT.lean` proves it strict.

Every `cedar-lean` library and test builds, and `CedarUnitTests` passes
(507/507). `CedarSymTests` (cvc5) passes 1204/1204.

## Production code (`cedar/`)

The Verus annotations are erased without the `verus` feature. The annotated
code stays in the fragment of Rust Verus supports, which shows in a few
places:

- the evaluator dispatches to one helper per kind of expression
  (`eval_and`, `eval_set`, ...), and evaluates set, record and call arguments
  with `for` loops; residuals are built by `*_residual` helpers;
- closures and `?`-combinators are `match`es, in the evaluator, the
  extension parsers, and `Policy::id` / `TemplateBody::condition`;
- `impl ExprBuilder for ast::ExprBuilder<T>` defines the trait's provided
  methods it uses, since Verus can only specify methods of the impl;
- sets and records are built by `value_set_from_vec` /
  `value_record_from_vec`, errors by small helpers, and regex captures and
  `chrono` arithmetic are in small helpers, so each can be specified.

The workspace lint `unsafe_code` is `deny` (Verus's generated code needs a
local `allow`). `cedar-policy-core` and `cedar-policy` have optional `vstd`
dependencies and a `verus` feature, which enables the `verification` module.
